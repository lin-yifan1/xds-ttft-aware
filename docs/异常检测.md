# 异常检测逻辑说明

本文档描述当前仓库中已经落地的异常检测实现，重点对应 [code/latency_detector.py](code/latency_detector.py) 的实际行为。当前版本的核心目标是：用 `TTFT / TPOT` 找到系统级时延异常事件，再用 `RPM / TPM / 输入长度 / 输出长度` 解释事件窗口中的主因用户。

## 1. 输入数据格式

检测入口是：

```python
detect_latency_anomalies(cfg: LatencyDetectorConfig, df: pd.DataFrame)
```

输入 `df` 是已经聚合好的明细数据。每行表示一个用户在一个时间窗内的指标。

必需列如下：

| 列名 | 含义 |
| --- | --- |
| `domain_id` | 用户标识 |
| `rpm` | 当前时间窗内请求量 |
| `tpm` | 当前时间窗内 token 吞吐量 |
| `ttft_avg` | 当前时间窗内 TTFT 平均值，单位 ms |
| `tpot_avg` | 当前时间窗内 TPOT 平均值，单位 ms |
| `prompt_tokens` | 当前时间窗内平均输入长度 |
| `completion_tokens` | 当前时间窗内平均输出长度 |
| `collect_time_std` | 标准化时间字段 |

## 2. 输入预处理

### 2.1 基础校验

`validate_latency_input()` 会执行：

- 检查必需列是否齐全
- `domain_id` 转成字符串，去掉空值和空白
- 数值列统一转成数值，无法解析的值填 `0.0`
- `collect_time_std` 优先按 `%Y-%m-%d %H:%M:%S` 解析
- 固定格式解析失败时，使用 `pandas.to_datetime` 宽松解析
- 无法解析时间的行会被丢弃
- 若没有任何有效行，直接抛错

### 2.2 重复数据折叠

如果同一 `domain_id + collect_time_std` 有多行数据，会折叠成一行：

| 指标 | 折叠方式 |
| --- | --- |
| `rpm` | 求和 |
| `tpm` | 求和 |
| `ttft_avg` | 按 `rpm` 加权平均，忽略 `ttft_avg = 0` 的点 |
| `tpot_avg` | 按 `rpm` 加权平均，忽略 `tpot_avg = 0` 的点 |
| `prompt_tokens` | 按 `rpm` 加权平均 |
| `completion_tokens` | 按 `rpm` 加权平均 |

`TTFT/TPOT = 0` 在当前实现里被视为“没有有效时延统计”，不参与时延均值计算。

## 3. 时间轴与矩阵构建

系统会从所有有效时间点推断时间粒度：

- 如果只有一个时间点，默认 `1h`
- 否则取相邻时间点之间的最小正间隔

然后生成从最早时间到最晚时间的连续 `time_index`。缺失时间窗会被补齐，矩阵中缺失位置填 `0.0`。

构建的用户矩阵包括：

- `rpm_matrix`
- `tpm_matrix`
- `ttft_matrix`
- `tpot_matrix`
- `prompt_matrix`
- `completion_matrix`

矩阵维度为：

```text
行：domain_id
列：time_index
```

## 4. 系统级序列

在用户矩阵基础上，系统构建以下系统序列：

| 序列 | 计算方式 |
| --- | --- |
| `system_rpm` | 所有用户 `rpm` 求和 |
| `system_tpm` | 所有用户 `tpm` 求和 |
| `system_ttft` | 所有用户 `ttft_avg` 按 `rpm` 加权平均，忽略 0 |
| `system_tpot` | 所有用户 `tpot_avg` 按 `rpm` 加权平均，忽略 0 |
| `system_prompt` | 所有用户 `prompt_tokens` 按 `rpm` 加权平均 |
| `system_completion` | 所有用户 `completion_tokens` 按 `rpm` 加权平均 |

事件触发只使用 `system_ttft` 和 `system_tpot`。

## 5. 系统事件判定

### 5.1 配置参数

默认配置来自 `LatencyDetectorConfig`：

| 参数 | 默认值 | 含义 |
| --- | ---: | --- |
| `ttft_sla` | `15000.0` | TTFT SLA，单位 ms |
| `tpot_sla` | `50.0` | TPOT SLA，单位 ms |
| `severe_ratio` | `7` | 重度异常倍率 |
| `mild_consecutive_windows` | `10` | 轻度超 SLA 需要连续命中的窗口数 |
| `event_merge_gap` | `0` | 事件合并允许的空白窗口数 |
| `max_events` | `5` | 最多保留事件数，`0` 表示不裁剪 |

Web 页面灵敏度通过 `LATENCY_SENSITIVITY_RATIOS` 改写 `severe_ratio`：

| 灵敏度 | `severe_ratio` |
| --- | ---: |
| `sensitive` | `4` |
| `balanced` | `7` |
| `relaxed` | `10` |

### 5.2 重度异常

单点重度异常直接触发异常：

```text
ttft_heavy = system_ttft >= ttft_sla * severe_ratio
tpot_heavy = system_tpot >= tpot_sla * severe_ratio
```

以默认均衡配置为例：

- TTFT 重度阈值为 `15000 * 7 = 105000 ms`
- TPOT 重度阈值为 `50 * 7 = 350 ms`

### 5.3 轻度持续异常

轻度异常只表示超过 SLA：

```text
ttft_mild = system_ttft > ttft_sla
tpot_mild = system_tpot > tpot_sla
```

但轻度异常必须连续出现至少 `mild_consecutive_windows` 个窗口才会被 `_mark_runs()` 标为异常。满足长度要求的整段轻度超标窗口都会被置为 `True`。

### 5.4 TTFT 和 TPOT 合并

每类指标先独立生成异常掩码：

```text
sys_anom_ttft = ttft_heavy OR mark_runs(ttft_mild, mild_consecutive_windows)
sys_anom_tpot = tpot_heavy OR mark_runs(tpot_mild, mild_consecutive_windows)
```

系统总异常点为二者并集：

```text
sys_anom = sys_anom_ttft OR sys_anom_tpot
```

因此，TTFT 或 TPOT 任一异常即可产生系统异常点，不要求同时命中。

### 5.5 事件窗口生成与裁剪

`_mask_to_events(sys_anom, event_merge_gap)` 会把异常点合并成事件窗口：

- 连续异常点会合并成同一个窗口
- 若 `event_merge_gap > 0`，间隔不超过该值的片段也会合并
- 当前默认 `event_merge_gap = 0`，即只合并真正相邻的点

事件过多时，`_cap_events()` 会按严重度保留前 `max_events` 个。严重度定义为窗口内：

```text
max(system_ttft / ttft_sla, system_tpot / tpot_sla)
```

最终输出：

- `events = [(start_hour, end_hour), ...]`
- `sys_event_mask`
- `sys_anom`
- `sys_anom_ttft`
- `sys_anom_tpot`

## 6. 基线计算

根因分析只为诱因指标建基线，不为 TTFT/TPOT 建根因基线。

用户级基线：

- `baseline_rpm`
- `baseline_tpm`
- `baseline_prompt`
- `baseline_completion`

系统级基线：

- `system_baseline_rpm`
- `system_baseline_tpm`
- `system_baseline_prompt`
- `system_baseline_completion`

基线计算方式：

```text
rolling mean over previous baseline_window_points
shift(1), past-only
min_periods = min_baseline_points
NaN -> 0.0
```

默认：

- `baseline_window_points = 24`
- `min_baseline_points = 6`

## 7. 事件内根因评分

### 7.1 事件范围

每个事件窗口 `[a, b]` 会根据其中 TTFT/TPOT 的异常情况确定 `rootcause_scope`：

| `rootcause_scope` | 含义 |
| --- | --- |
| `ttft_only` | 事件窗口内有 TTFT 异常，没有 TPOT 异常 |
| `tpot_only` | 事件窗口内有 TPOT 异常，没有 TTFT 异常 |
| `both` | 事件窗口内 TTFT 和 TPOT 都有异常 |

### 7.2 四类正向变化量

对每个事件窗口和每个用户，计算四类相对基线的正向变化：

```text
rpm_excess_window        = max(rpm - baseline_rpm, 0)
tpm_excess_window        = max(tpm - baseline_tpm, 0)
prompt_delta_window      = max(prompt_tokens - baseline_prompt, 0)
completion_delta_window  = max(completion_tokens - baseline_completion, 0)
```

这些变化量会在事件窗口内按时间求和：

```text
rpm_excess_sum
tpm_excess_sum
prompt_delta_sum
completion_delta_sum
```

再在所有用户之间分别归一化：

```text
rpm_excess_ratio
tpm_excess_ratio
prompt_delta_ratio
completion_delta_ratio
```

注意：输入长度和输出长度当前不乘以 `RPM`，只看它们相对自身历史基线是否变长。

### 7.3 按事件范围加权

不同事件范围使用不同权重：

| 事件范围 | RPM | TPM | 输入长度变化 | 输出长度变化 |
| --- | ---: | ---: | ---: | ---: |
| `ttft_only` | 0.35 | 0.15 | 0.40 | 0.10 |
| `tpot_only` | 0.10 | 0.25 | 0.15 | 0.50 |
| `both` | 0.225 | 0.20 | 0.275 | 0.30 |

用户综合分：

```text
score =
  w_rpm * rpm_excess_ratio
+ w_tpm * tpm_excess_ratio
+ w_prompt * prompt_delta_ratio
+ w_completion * completion_delta_ratio
```

设计含义：

- TTFT 事件更关注请求量和输入长度
- TPOT 事件更关注 token 吞吐和输出长度
- 两者都异常时使用折中权重

## 8. Culprit 筛选和峰值点

每个事件窗口内，用户按 `score` 从高到低排序。筛选规则：

- `score <= 0` 时停止
- 第一个 culprit 只要求分数为正
- 后续候选若 `score_ratio < culprit_min_ratio`，停止
- 最多保留 `culprit_top_k = 3`
- 累计 `score_ratio >= culprit_cum_ratio = 0.8` 后停止

对每个入选 culprit，代码会在事件窗口内计算每个小时的局部综合分 `local_score`，并选择最高的小时作为 `peak_hour`：

```text
flags[user, peak_hour] = True
```

当前版本只标记 culprit 的代表性峰值点，不会把整个事件窗口或完整 episode 都标成用户异常。

每个 culprit 记录包含：

- `user_id`
- `score`
- `score_ratio`
- 四类贡献占比
- `length_signal`
- `driver_signal`
- `peak_hour`
- 峰值小时的 `rpm / tpm / prompt_tokens / completion_tokens / ttft / tpot`
- `first_active_hour`
- `is_new_user_join`

## 9. 事件级诱因判断

事件级诱因判断使用系统级四类指标相对系统基线的正向偏移：

```text
positive_shift_score =
  正向增量总和 / (基线绝对值总和 + 正向增量总和 + EPSILON)
```

得到：

- `rpm_shift_score`
- `tpm_shift_score`
- `prompt_shift_score`
- `completion_shift_score`

按事件范围解释：

| 事件范围 | 流量侧 | 长度侧 | 可能输出 |
| --- | --- | --- | --- |
| `ttft_only` | `rpm_shift_score` | `prompt_shift_score` | `rpm_rise_dominant` / `input_shift_dominant` / `rpm_input_mixed` |
| `tpot_only` | `tpm_shift_score` | `completion_shift_score` | `tpm_rise_dominant` / `output_shift_dominant` / `tpm_output_mixed` |
| `both` | `0.5*rpm + 0.5*tpm` | `0.5*prompt + 0.5*completion` | `traffic_family_dominant` / `length_family_dominant` / `traffic_length_mixed` |

判定边界：

- 一侧得分至少是另一侧的 `DOMINANCE_RATIO = 1.2` 倍，则认为该侧 dominant
- 否则为 mixed
- 两侧都不大于 0 时为 `unclear`

事件报告中会输出：

- `driver_signal`
- `traffic_driver_score`
- `length_driver_score`
- `traffic_driver_ratio`
- `length_driver_ratio`
- `driver_breakdown`

## 10. 用户级诱因标签

每个 culprit 也会生成用户级 `driver_signal`。它不使用系统 shift score，而是直接使用该用户自己的四类贡献占比。

此外还有 `length_signal`，用于更细地描述输入输出长度变化：

| 标签 | 含义 |
| --- | --- |
| `traffic_dominant` | 流量侧更占主导，或没有明显长度变化 |
| `io_shift_joint` | 输入和输出长度都有较明显变化 |
| `input_shift_dominant` | 输入长度变化更主导 |
| `output_shift_dominant` | 输出长度变化更主导 |
| `length_shift_mixed` | 长度侧有变化，但输入输出主导性不明显 |

## 11. 新用户加入事件

检测器会先计算每个用户首次出现正流量的位置：

```text
first_active_hour = 第一个满足 rpm + tpm > 0 的时间窗
```

如果某个 culprit 的 `first_active_hour` 落在当前事件窗口 `[a, b]` 内，则认为它是新用户加入：

- culprit: `is_new_user_join = True`
- event: `is_new_user_join_event = True`
- event: `event_variant = new_user_join_event`
- event: `new_join_users` 记录这些用户

否则：

- `event_variant = traditional_latency_event`

## 12. 输出结果

`detect_latency_anomalies()` 返回：

- `time_index`
- `time_step_minutes`
- `user_ids`
- 用户矩阵：`rpm / tpm / ttft / tpot / prompt_tokens / completion_tokens`
- 系统序列：`system_rpm / system_tpm / system_ttft / system_tpot / system_prompt_tokens / system_completion_tokens`
- 异常掩码：`sys_anom / sys_anom_ttft / sys_anom_tpot / sys_event_mask`
- `events`
- `event_reports`
- `flags`
- `records`
- `system_stats`
- `config_echo`
- `detection_timings`

## 13. Records 生成

`records` 只包含至少被 `flags` 命中过一次的用户。当前 `flags` 来自 culprit 的峰值点。

每条记录包括：

- `user_id`
- `hit_count`
- `hit_hours`
- `reason`
- `avg/p95/max rpm`
- `avg/p95/max tpm`
- `avg/p95/max ttft`
- `avg/p95/max tpot`
- `avg_prompt_tokens`
- `avg_completion_tokens`

`reason` 来自该用户参与过的事件范围：

- `ttft_only`
- `tpot_only`
- `both`
- `new_user_join`

如果没有可用 reason，则兜底为 `latency_rootcause`。

## 14. 耗时统计

检测器内部会记录：

- `prepare_input_seconds`
- `dedupe_seconds`
- `time_index_seconds`
- `matrix_build_seconds`
- `system_series_seconds`
- `event_detection_seconds`
- `baseline_seconds`
- `rootcause_seconds`
- `records_seconds`
- `stats_seconds`
- `detection_total_seconds`

这些字段用于页面展示和性能定位。

## 15. 当前实现边界

当前 `latency_detector.py` 没有实现旧版文档中的以下逻辑：

- 基于系统 RPM 总量的季节性 ratio 门
- robust z / MAD 检测
- 系统流量增长率 burst 检测
- 用户 share z、abs z、growth burst 复合打标
- episode 峰值回填
- 事件外用户异常检测

当前实现的“严格根因”体现在根因评分只遍历 `events`，而不是通过一个独立的 `strict_rootcause` 配置项控制。
