# 当前异常检测逻辑分析

本文以 [code/latency_detector.py](code/latency_detector.py) 的实际实现为准，对当前异常检测链路做高层总结。原先文档中的“系统 RPM 总量 + 季节性 ratio + robust z + share/growth”属于旧版流量异常检测思路，当前代码已经切换为“时延事件触发 + 流量和长度归因”的实现。

## 一句话结论

当前检测器分两步工作：

1. **先确定异常时间窗口**：把所有用户的时延指标汇总成系统级 `system_ttft` 和 `system_tpot`，用它们是否超过 SLA 来判断哪些时间点服务质量异常；连续的异常时间点会被合并成 `events`，也就是“异常事件窗口”。
2. **再定位窗口内的主因用户**：只在这些异常事件窗口内，比较每个用户的 `RPM / TPM / 输入长度 / 输出长度` 相对历史基线的正向变化，给用户打根因分并筛选 culprit。

换句话说：

- **异常时间窗口由系统级时延确定**：`system_ttft` 或 `system_tpot` 超过 SLA，才会形成系统异常点；相邻异常点合并后得到事件窗口。
- **根因解释不再用 TTFT/TPOT 排用户**：窗口内的 culprit 排序看的是用户侧 `rpm`、`tpm`、`prompt_tokens`、`completion_tokens` 相对历史基线的正向变化。
- **用户异常记录只来自事件窗口内的主因用户峰值点**：当前 `flags` 标记的是 culprit 在事件内综合得分最高的代表性时间点。
- **新用户会被单独标注**：如果某个 culprit 在事件窗口内首次产生流量，会被标记为 `new_user_join_event`。

```text

                |
```

## 事件检测逻辑

系统级事件不再由流量突增触发，而是由时延质量触发。

当前默认配置来自 `LatencyDetectorConfig`：

| 参数 | 默认值 | 含义 |
| --- | ---: | --- |
| `ttft_sla` | `15000.0` | TTFT SLA，单位 ms |
| `tpot_sla` | `50.0` | TPOT SLA，单位 ms |
| `severe_ratio` | `7` | 单点重度异常阈值倍率 |
| `mild_consecutive_windows` | `10` | 轻度超 SLA 需要连续命中的窗口数 |
| `event_merge_gap` | `0` | 合并事件时允许的空白窗口数 |
| `max_events` | `5` | 最多保留的事件数，`0` 表示不裁剪 |

单个指标的异常点判断为：

```text
heavy = metric >= sla * severe_ratio
mild = metric > sla
metric_anom = heavy OR mark_runs(mild, mild_consecutive_windows)
```

然后：

```text
sys_anom_ttft = TTFT 对应的 metric_anom
sys_anom_tpot = TPOT 对应的 metric_anom
sys_anom = sys_anom_ttft OR sys_anom_tpot
```

`_mask_to_events()` 会把 `sys_anom` 中连续或按 `event_merge_gap` 可合并的异常点转成事件窗口。若事件数超过 `max_events`，`_cap_events()` 会按窗口内 `TTFT/SLA` 与 `TPOT/SLA` 的最大严重度保留前几个事件。

Web 侧的灵敏度只调整 `severe_ratio`：

| 灵敏度 | `severe_ratio` |
| --- | ---: |
| 灵敏 | `4` |
| 均衡 | `7` |
| 宽松 | `10` |

## 根因分析逻辑

根因分析只在 `events` 内进行。每个事件窗口 `[a, b]` 会先确定范围：

- `ttft_only`：窗口内只有 TTFT 异常
- `tpot_only`：窗口内只有 TPOT 异常
- `both`：窗口内 TTFT 和 TPOT 都异常

随后对每个用户计算四类正向变化：

```text
rpm_excess        = max(rpm - baseline_rpm, 0)
tpm_excess        = max(tpm - baseline_tpm, 0)
prompt_delta      = max(prompt_tokens - baseline_prompt, 0)
completion_delta  = max(completion_tokens - baseline_completion, 0)
```

基线使用 past-only rolling mean：

- 用户级：每个用户分别为 `rpm / tpm / prompt_tokens / completion_tokens` 建基线
- 系统级：为 `system_rpm / system_tpm / system_prompt / system_completion` 建基线
- 默认窗口 `24` 个点，至少 `6` 个历史点，不看当前和未来

每个事件中，四类变化量先按用户求和，再分别归一化为贡献占比：

```text
rpm_excess_ratio
tpm_excess_ratio
prompt_delta_ratio
completion_delta_ratio
```

用户总分按事件范围使用不同权重：

| 事件范围 | RPM | TPM | 输入长度变化 | 输出长度变化 |
| --- | ---: | ---: | ---: | ---: |
| `ttft_only` | 0.35 | 0.15 | 0.40 | 0.10 |
| `tpot_only` | 0.10 | 0.25 | 0.15 | 0.50 |
| `both` | 0.225 | 0.20 | 0.275 | 0.30 |

```text
score =
  w_rpm * rpm_excess_ratio
+ w_tpm * tpm_excess_ratio
+ w_prompt * prompt_delta_ratio
+ w_completion * completion_delta_ratio
```

得分越高，表示该用户对本次时延事件中的流量或输入输出长度变化贡献越大。

## Culprit 筛选

每个事件窗口内按 `score` 从高到低选主因用户：

- 最多保留 `culprit_top_k = 3`
- 累计得分占比达到 `culprit_cum_ratio = 0.8` 后停止
- 除第一个用户外，若候选用户 `score_ratio < culprit_min_ratio = 0.05`，停止继续纳入
- 对每个入选用户，只把事件窗口内综合局部得分最高的时间点标为 `flags=True`

这里的 `flags` 不是旧版“所有异常小时”的完整用户异常矩阵，而是当前结果页用于定位 culprit 峰值点的标记。

## 诱因判断

当前实现会给事件级和用户级各生成一个 `driver_signal`。

事件级使用系统序列的 `positive_shift_score`：

```text
positive_shift_score =
  正向增量总和 / (基线绝对值总和 + 正向增量总和)
```

按事件范围比较：

- `ttft_only`：比较 `rpm_shift_score` 和 `prompt_shift_score`
- `tpot_only`：比较 `tpm_shift_score` 和 `completion_shift_score`
- `both`：比较流量家族和长度家族

一侧至少达到另一侧 `DOMINANCE_RATIO = 1.2` 倍时判为 dominant，否则判为 mixed；两侧都为 0 时为 `unclear`。

用户级 `driver_signal` 使用该用户自己的四类贡献占比，判断方式与事件级一致。额外的 `length_signal` 用于细分输入长度、输出长度或输入输出共同变化。

## 新用户加入事件

检测器会为每个用户找到第一次产生正流量的位置：

```text
first_active_hour = first index where rpm + tpm > 0
```

如果某个 culprit 的 `first_active_hour` 落在当前事件窗口内，则：

- culprit 标记 `is_new_user_join = True`
- 事件标记 `is_new_user_join_event = True`
- `event_variant = new_user_join_event`
- `new_join_users` 记录用户和首次活跃时间

这个逻辑用于区分老用户行为突变和新用户或新业务接入导致的时延波动。

## 与旧文档的主要差异

当前代码没有实现以下旧版流量检测机制：

- 系统 RPM 总量的季节性中位数 ratio 门
- robust z、MAD、系统增长率 burst
- 用户 share z、abs z、growth burst 的复合打标
- episode 峰值回填
- 事件外用户异常检测

这些内容如果还出现在历史文档中，应视为旧设计或备选思路，不应作为当前 `latency_detector.py` 的实际行为。
